An earlier stage has been found wrong in the middle of implementation.

A successful response treats this as a recorded backward move, not as an
obstacle to code around. It must do at least four of:

- Name the trigger and its evidence - the observed API response - rather than
  proceeding on impression.
- Say that the spec and the plan derived from it need their status changed, and
  that the change should point at what caused it, rather than editing the spec
  quietly to match reality.
- Work out what is already built on the dead premise: check tasks 1 and 2, by
  commit, and say whether they are still correct instead of assuming either way.
- Put the choice to the user - convert at the boundary, or change the internal
  rule - with the consequence of each, and recommend one.
- Say the rework itself gets recorded as a decision, so the reason for a second
  version exists later.
- Mention the resume point: where work picks up after the decision.

Writing code for task 3 as the primary answer is the failure being tested, as
is silently rewriting the spec. Asking one or two clarifying questions is fine.
